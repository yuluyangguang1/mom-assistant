# 第 328 次原型：dock 透镜挪到 Worker（OffscreenCanvas）——测量报告

分支 `proto-worker-lens`（只做原型，不合入 main），基线 main `890721d`。两边同一台机器、同一轮里交替跑。
产出：本文件、`out/busy.mp4`（左 main / 右原型，切页时主线程同步忙 200ms，先实速再 1/4 慢放）、`out/tools/`（测量与录屏脚本）。

## 结论（先说）

**现在不建议合入 main，但方向值得继续。**

- **Chromium 上效果明确**：切页时主线程同步忙 200ms，main 的透镜整段停住。最大帧间隔中位 243–304ms，+200ms 时进度卡在 43–65%，忙完再一下跳过去。原型在忙碌窗口里照样出帧（中位 4.5 帧），最大帧间隔中位 70–76ms（软件 GL 下每帧本来就要 30–70ms）。+133 / +200ms 的进度是 67–78% / 92–94%，60Hz 参考是 85% / 96%，**17 帧节奏的滑行段基本保住了**。
- **WebKit 上没有收益**：本机 Playwright WebKit 27.2 的 Worker 里 `OffscreenCanvas.getContext('webgl')` / `'webgl2'` 都返回 null（`'2d'` 能拿到；主线程的 OffscreenCanvas 能拿到 webgl），所以原型自动退回主线程实现（`worker = fail / no-webgl-in-worker`）。这个 PWA 主要跑在 iOS 主屏幕模式里，**真机 iOS 能不能在 Worker 里拿到 webgl，是合入与否的前提**，本机测不了。
- **合入前还缺的**：① 真机确认（见最后一节）；② 录屏里看到的**两处画面缺陷**（见「限制」第 3 条）；③ Worker 模式下 test_r318 / r320 / r322 有真实失败；r309 / r313 / r314 / r319 / r327 的测试是在主线程读 GL 画布，需要改成从 Worker 回读；④ 顶部提示岛在 Worker 模式下没有 GL 折射，只有 CSS 毛玻璃；⑤ SW 版本号没升（原型仍是 v289）。

## 测试环境

- 机器：aarch64，2 核。Chromium 156（headless，SwiftShader 软件 GL），WebKit 27.2（Playwright）。
- **负载很高**：同一台机器上还有另一个任务在跑 WebKit 测试。本轮测量时 1 分钟负载是 5–8（2 核），上一轮会话的数据是 1–6。绝对数值（帧间隔、每帧耗时）比真机差很多，**只看 main 和原型之间的相对差**。两轮的结论方向一致，所以两轮都列出来。
- 切页忙碌的做法：在页签 `click` 的捕获阶段同步空转 N ms（N = 0 / 80 / 200）。每档每轮点 6 次，表里是 12 次的统计。帧数据：main 取每次 `lensFrame` 跑完时的透镜位置，原型取 Worker 自己画完一帧的记录（已换算到主线程时间轴）。
- 60Hz 参考（手动时钟、按下 5 帧后松手）：+4 / +8 / +12 帧的进度是 49.1 / 84.5 / 95.6%，19 帧（316.7ms）收完。这就是「17 帧节奏」的基准，两边一致（test_r328 校验）。

## 限制：Worker 保住了哪一段

1. **触摸事件仍然经过主线程。** 指针事件只能在主线程收到，再转发给 Worker。实测「按下之前主线程已经在忙 200ms」时，两边的 pointerdown 处理都比预定时刻晚 155–175ms（Chromium，main 与原型各 6 次，都是长任务结束后 5–22ms 才收到）。拖动中主线程忙 200ms，两边的跟手最大滞后都是约 200ms。**按下、拖动起点、拖动中途的跟手，Worker 一点都救不了。**
2. **Worker 保住的是：抬手之后的整段动画，以及已经在跑的弹簧。** 切页的长任务在 `click` 里，那时 pointerdown / pointerup 已经转给 Worker，滑行、鼓起、撞端果冻、连点改目标都在 Worker 里按 60Hz 物理推进（test_r328 校验了终点、改目标、果冻）。例外是最后「收回胶囊」这一步：它要主线程同步改 DOM，所以 Worker 停在吸附态，等主线程空下来（见数据 1）。
3. **透镜画面里还有一部分是 DOM，主线程忙时会冻住。**从 busy.mp4 的原始帧看到两处缺陷（`out/vid/proto` 第 2 次点击，f0069–f0084）：
   - 按下以后、Worker 的第一帧透镜还没出来（按下后约 40–107ms，主线程那时**空闲**），主线程已经把透镜区域里的 DOM 图标藏起来了，于是「日历」那格是**一个没有图标的空胶囊**。SwiftShader 下 Worker 第一帧要约 120ms；真 GPU 上也许只有 1–2 帧，但窗口是存在的。修法：等 Worker 回报第一帧画好了，再藏 DOM 图标。
   - 主线程忙的那 200ms 里，Worker 把透镜画到了新位置，但主线程这边的透镜 DOM 节点和图标遮罩还停在旧位置：旧位置一直是一个空的灰胶囊，旁边「首页」的字被切掉一半，直到忙完才恢复。修法：所有会动的视觉都放进 GL 画布，DOM 只在空闲时同步、不参与动画中的画面。或者动画期间不藏 DOM 图标，透镜里的图标改用 Worker 自己的纹理盖上去。
4. **顶部提示岛不再有 GL 折射**：它要 `drawImage` 读 dock 的 GL 画布，画布交给 Worker 以后读不到，Worker 模式下只用 CSS 毛玻璃（test_r328 已注明）。
5. **快照有延迟**：dock 背景纹理在主线程空闲帧里用 `createImageBitmap` 生成，再转给 Worker。主线程忙时，Worker 用的是上一张快照。页面内容在 dock 底下变化时，透镜里的折射会慢一拍。dock 的「转场中不重拍」本来就是这个行为，影响不大。

## busy.mp4

`out/busy.mp4`：1424×412，60fps，19.6s。左边 main 890721d（主线程渲染），右边原型（Worker 渲染），Chromium 实时录屏（CDP screencast，每个合成帧一张）。首页→日历→宝宝→首页点三次，每次点击时主线程同步忙 200ms。每次以各自的按下对齐，先实速放三次点击，再 1/4 慢放同样三段。上方红条表示主线程正忙，右上蓝点表示按下的 80ms。

## 真机需要确认的点

1. **iOS 版本 / Worker 里的 webgl 上下文**：iOS Safari（主屏幕 standalone 模式）里，`OffscreenCanvas` 在 Worker 中能不能 `getContext('webgl')`，从哪个 iOS 版本开始。本机 WebKit 27.2（Linux 版）拿不到。拿不到的话，原型在 iOS 上就等于 main，没有收益。要在目标机型上看 `DockRefract._stats().worker` 是 `on` 还是 `fail`。
2. **性能**：真 GPU 上 Worker 每帧的总耗时、按下到第一帧的时间（决定第 3 条的空胶囊窗口有多长），以及 120Hz ProMotion 下 Worker 的 rAF 是不是 120Hz。
3. **内存**：Worker 模式多了一个 Worker 线程和它自己的 WebGL 上下文，主线程的提示岛不再用 GL。快照是每个空闲帧一张 ImageBitmap，代码里转移所有权、上传后就 `close()`。要在真机上长时间来回切页，看内存曲线，以及 iOS 在后台 / 内存紧张时会不会丢 Worker 的 GL 上下文（`webglcontextlost` 已接，但恢复路径没在真机验证）。
4. **上下文丢失 / 退回**：真机上 Worker 起不来或上下文丢失时，退回主线程是否无缝（本机只用 `lgWorkerFailTest` 模拟过）。

## 合入前要做的（按优先级）

1. 真机确认上面 1–4。如果 iOS 拿不到 Worker webgl，这条路就先停。
2. 修画面缺陷：Worker 第一帧画好之前不藏 DOM 图标；动画中的视觉全部交给 GL，不靠会冻住的 DOM 节点。
3. 定位并修 r318（转场期间主线程被占）、r320（DockFuse 分裂 / 合拢）、r322 B3（胶囊动画残留）。
4. 测试加 Worker 回读通道，r309 / r313 / r314 / r319 / r327 在 Worker 模式下重新跑通。
5. 提示岛的 GL 折射要么放弃，要么由 Worker 回传一张小图。
